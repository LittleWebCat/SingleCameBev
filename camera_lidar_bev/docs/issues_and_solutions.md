# Previous issues and solutions

Updated **2026-10-15**. This is the troubleshooting history for the front-camera/Ouster BEV project, recording, mapping/localization, Pure Pursuit and the optional DBW bridge. It summarizes the conversation and retained source, configuration and reports. Historical measurements describe their own runs, not the current state of connected hardware.

**Implemented** means the software change or configuration exists. **Provisional** means it runs but physical accuracy or behavior still needs independent evidence. **Archived** means an experiment was removed from normal operation. Where the original cause was not established or its logs are unavailable, that is stated explicitly.

From `camera_lidar_bev/`, install persistent DDS settings once:

```bash
sudo bash tools/setup_dds_transport.sh
```

Then the documented five-minute dense GPS capture command is:

```bash
ROS_DOMAIN_ID=1 bash tools/collect_camera_lidar.sh \
  --lidar-mode 2048x10 --gps \
  --duration 300 --scene '10hz_gps_mapping'
```

Keep the rig still for approximately 10 seconds after recording begins so mapping can initialize. See [recording](camera_lidar_recording.md) and [LiDAR bring-up](lidar_bringup.md) for preflight, logs and offline inspection.

## 6. DBW bridge review, fixes and engagement behavior

The optional sibling `bev_bridge/` was reviewed after the perception/mapping work. Its original permissive input/serial behavior required changes before exposing a live command path.

| Issue found or encountered | Implemented change | Evidence or limit |

| Invalid JSON/status could leave a cached positive target; arrays could raise an uncaught schema error. | Strictly validate object schema, duplicate keys, exact booleans, finite numbers and required fields. ## 8. What remains unresolved

- Independent intrinsic/extrinsic accuracy, surveyed vehicle/antenna transforms and physical camera/LiDAR/GNSS acquisition-clock alignment.
- Reliable distant-object/pedestrian recall and size/yaw accuracy on Ouster data; increasing display range does not extend a model's trained range.
- Sustained recording loss and end-to-end latency measurements for each selected sensor/mode/workload combination.
- Loop closure, validated global localization accuracy, a surveyed HD map and lane/traffic-rule topology.
- Moving vehicle-frame occupancy, persistent object tracking/prediction, obstacle-aware planning, and a dedicated BEV training-sample exporter. Raw displayed points are not a learned planner feature tensor.
- Independent DBW firmware/feedback/braking verification and measured closed-loop vehicle tracking performance. Sending a command is not a measurement of its physical effect.
- **Vehicle speed does not follow the commanded speed** (up to 17.6–21.6 mph against a 7 mph cap; stationary while 5–7 mph is commanded). Firmware speed-hold, `0x284` delivery and operator pedal input must be checked before further runs at speed; until then the software cap does not bound vehicle speed.
- The `hardware.json` steering rate (280 degrees/s) exceeds the operator-reported 200 degrees/s firmware limit; actual firmware rate behavior is unknown.
- The bridge records `invalid_tracking_valid` without the tracker's specific state (off route, heading, pose jump, endpoint); diagnosing it requires the live tracker status.
- The external profile's steering request exceeds its validation policy and blocks that profile's hardware startup.
- The dense `2048x10` LiDAR profile still contributes about 143 ms of the ~213 ms input latency.

The legacy camera/multi-camera BEV code remains separate. No migration of that code, firmware flashing, recording, live restart, vehicle engagement or GitHub upload is performed by this documentation update.
